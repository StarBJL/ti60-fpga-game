## 三、每一步具体讲什么

### 第 1 步：用一句话定义项目

**这一段要讲清：**平台、输入输出，以及软硬件协同的目标。

可直接使用的开场：

> 我做的是一个基于 Efinix Ti60 FPGA 和 Sapphire RISC-V 软核的裸机多媒体游戏平台。它通过多种键盘输入控制游戏，用 FPGA 图形引擎在共享 DDR 中绘制画面，输出 720p HDMI 视频和双声道声音，并通过上位机观察不同负载下的性能。

然后补充目标：在有限软核性能和共享存储带宽下，让游戏状态更新、绘图、视频扫描和音频供样协同运行。

展示：README 首页和一张当前运行器预览。若使用本机生成的画面，明确说明它是软件渲染预览。

这一段暂时不展开寄存器、DMA 突发长度和角色数值，给后面的架构保留空间。

### 第 2 步：先展示可观察的功能

**这一段要讲清：**每个演示场景在系统中承担什么作用。

建议依次展示：

1. 三人萝卜游戏：体现多输入、复杂场景、特效和音频同时运行。
2. 弹幕压力场景：体现大量重复精灵、尺寸变化与边缘裁剪。
3. 方块场景：体现大量填充操作和 FTAB。
4. 图片扫描／循环：体现整图复制和连续显示。

东方风格弹幕可以作为补充展示，用来说明另一套游戏状态机仍能共用图形和音频接口。

推荐讲法：

> 游戏给系统提供完整的交互负载，弹幕和方块则把图形压力拆成更容易比较的实验。这样既能展示最终画面，也能定位性能差异来自哪里。

展示过程中不要把上位机填入的对象数量立即称为“稳定 60 帧最大数量”；数量、实际活跃对象和呈现帧率应同时观察。

### 第 3 步：用一张架构图解释分工

**这一段要讲清：**CPU 负责什么，硬件负责什么，DDR 为什么是中心。

按三条线讲：

- 控制线：输入 → RISC-V → 游戏状态／绘图命令／音效事件。
- 图像线：源素材／绘制表 → BitBlt → 帧缓冲 → HDMI DMA → 显示。
- 音频线：声音库 → 混音器 → 异步 FIFO → HDMI 音频包。

可直接使用的表述：

> CPU 不需要为每个输出像素都执行同样的运算。它把需要画什么、画在哪里、怎样混合组织成命令；图形引擎负责按这些命令处理大量像素。DDR 同时保存程序数据、素材、命令表和帧缓冲，因此调度和带宽也成为设计的一部分。

代码定位：顶层 `rtl/ddr3_example_top.v`，软件入口 `game/src/main.c`，图形入口 `gfx.c → gfx_hw.c → blit.c`。

常见追问：“哪些不是你从零写的？”可明确区分厂商 FPGA／SoC／DDR 相关 IP、应用与自定义图形音频模块、第三方运行环境及素材来源，按仓库实际文件说明贡献范围。

### 第 4 步：解释时钟和内存边界

**这一段要讲清：**225 MHz 是核心域的工作频率，系统中还存在其他时钟。

推荐展示 README 的时钟表和内存表，只突出三项：

- 核心域 225 MHz；HDMI 像素域 74.375 MHz；音频输出节拍 48 kHz。
- 一帧 720p RGB565 为 1,843,200 字节。
- 帧缓冲、声音区、运行素材区和压缩素材区分别规划，避免互相覆盖。

可直接讲：

> 这里的 225 MHz 不是显示器每秒更新 225 百万帧。它表示 CPU 和部分硬件逻辑的时钟频率；视频扫描与声音采样由各自的节拍控制。软件还必须用与硬件一致的 CLINT 频率换算时间，否则连显示出来的毫秒和 FPS 都会有系统误差。

追问时可举例：若硬件 225 MHz、换算却用 200 MHz，耗时会被放大 12.5%。

### 第 5 步：沿着一帧的生命周期讲时序

**这一段要讲清：**“已提交”“已绘制完成”“已显示”是不同状态。

按输入、逻辑、绘制命令、硬件处理、完成等待、同步翻页六个动作展开，随后解释逻辑重叠：提交之后 CPU 可以做后续逻辑，但不能覆盖仍被硬件读取的数据。

推荐讲法：

> 为了让软件和硬件重叠工作，我不能只关心函数返回时间。硬件还可能在异步读取上一帧的表和素材，因此需要保护它们的生命周期；翻页也必须等待对应帧完成。工程使用四个帧缓冲，并检查当前扫描、待翻页和在途绘制的地址，减少互相覆盖。

展示：README 的帧时序图；展开 `main.c` 中 `pend_fb`、`pend_seq` 和完成等待附近的代码。

四个帧缓冲并不会直接让性能变成四倍，它们提供的是重叠执行所需的存储与时序余地。

### 第 6 步：讲清楚 BitBlt 的具体能力

**这一段要讲清：**加速对象不是笼统的“游戏”，而是明确的像素操作与提交机制。

从简单到复杂介绍：

1. FILL：纯色矩形；COPY：图像复制。
2. 色键：跳过背景色；全局 Alpha／A8：半透明与柔和边缘；加法混合：发光效果。
3. SLOT／DRAW：复用精灵参数。
4. TAB：硬件读取精灵位置表；FTAB：硬件读取矩形填充表。
5. K 通路、宽通路和窄通路按条件分工。

最值得展示的例子是边缘裁剪：

```text
A、B 屏内；C 需裁剪；D、E 屏内
→ TAB(A,B) → 裁剪 C → TAB(D,E)
```

可直接讲：

> 如果只因为一个弹幕碰到边缘，就让整张表回到 CPU 逐项展开，大部分本来可以快速提交的对象也被拖慢。现在按原顺序把连续屏内对象组成 TAB 段，裁剪对象单独处理，既保留效率，也保留遮挡顺序。

不要把 8 像素／拍直接换算成实板持续吞吐；这是特定内部路径的理想处理能力，外部存储和其他阶段仍会限制整机表现。

### 第 7 步：讲 DDR 优化，而不只讲提高频率

**这一段要讲清：**为什么减少访存和命令开销比只看主频更能解释性能。

先给出计算：单次全帧读取按 60 帧约 110.6 MB/s，写入和扫描各一次就约 221.2 MB/s，尚未计入其他素材和音频。

随后解释三个措施：

- 批量表减少 CPU 逐对象参数展开。
- 源缓存复用重复精灵和字形。
- 16 行片上分带窗口减少目标颜色的反复 DDR 读改写。

推荐讲法：

> 透明对象需要已有背景颜色才能混合。如果每一层都从 DDR 读回再写回，流量会快速增加。分带合成把当前区域的目标颜色放在片上，按顺序叠加对象后再写回。它没有消除所有带宽需求，但改变了最昂贵的目标访问方式。

可补充字体经验：把英文数字统一改为 A8 会失去原色键路径的优势；当前恢复旧字形路径并增加标签缓存，说明视觉效果与硬件路径需要一起设计。

### 第 8 步：解释 HDMI 音频为什么不会跟着核心升频变调

**这一段要讲清：**供样速度与播放节拍分离。

推荐讲法：

> 混音器在核心时钟域中工作，看到 FIFO 水位不足就继续产生采样；HDMI 在像素时钟域按固定音频节拍取走采样。因此核心从 200 MHz 改为 225 MHz，增加的是处理预算，而不是把声音按 1.125 倍速度播放。

展示公式：`74375000 × 6144 / (128 × 74375) = 48000 Hz`。

再用当前修复举一个工程例子：SB6 要按左右声道组织 PCUV 位；VSYNC 输出边沿也需要符合当前同步关系。当前位流修正了这些位置，并有指定范围的 TMDS 仿真对照。

边界要讲明：完整一帧与 R7 参考一致不等于完成所有 HDMI 接收设备兼容性测试。

### 第 9 步：展示上位机如何让实验可重复

**这一段要讲清：**上位机既是控制器，也是实验条件记录入口。

展示一次操作：选场景 → 选尺寸与数量 → 等待 ACK 和状态核对 → 观察一段新的统计窗口。

推荐讲法：

> 上位机通过本地服务连接串口，不直接替代 FPGA 绘图。它帮助我固定后端、缓存、分带、透明度和数量等条件，再记录设备真正生效的状态。这样同一个预设才具有比较意义。

说明当前 1.1 倍取百位规则；25px 后续单独设为 11,000。把这些称为“压力目标”或“预设负载”，后续结合实测确定可持续帧率。

### 第 10 步：把硬件能力对应到游戏体验

**这一段要讲清：**应用如何调用系统能力，而不是逐个背诵技能名称。

可以选三个有代表性的例子：

- 角色被动与升级：展示 CPU 状态机、条件、冷却及事件管理。
- 大招：展示稳定素材复用、Alpha、有限粒子、阶段动画及有界碰撞范围。
- Boss 配音：展示音频事件调度、语音优先级和背景音乐压低。

推荐讲法：

> 蓝虎和凤凰并不是每帧重新生成的大图。它们先由母图生成有限的展开阶段，运行时切换阶段、位置和透明度，并叠加剑气或樱花。这既保留了层次，也让内存和绘制成本可控。配音更换时保留采样点数，避免声音长度变化破坏动画与伤害节拍。

介绍当前小怪密度时，区分“对象池 384 槽”“无尽关最多 360 只小怪”和“每帧绘制／碰撞成本”，不要把它们简化成一个未经测量的性能结论。

### 第 11 步：展示证据，并说明证据能够证明什么

**这一段要讲清：**时序、编译、仿真和实板测量各自回答不同问题。

建议只展示一张清晰表：

| 结果 | 可说明什么 | 不能直接说明什么 |
|---|---|---|
| setup +0.063 ns、hold +0.012 ns | 当前实现报告列出的约束关系通过 | 所有板卡和未约束接口都已验证 |
| Debug／Release ELF 编译、载荷核对 | 交付程序和素材配对、布局可链接 | 实板重负载必然稳定 60 帧 |
| 400 秒无尽回归、渲染检查 | 被覆盖条件下逻辑与内存检查通过 | 实际 HDMI 图像和音质已人工验收 |
| 实板日志 | 对应 BIT／ELF 和条件下的实际表现 | 更换条件后的表现完全相同 |

推荐讲法：

> 我分别记录逻辑、提交、排队等待、尾部等待和实际呈现，避免只看一个平均 FPS。时序报告说明这一版实现满足列出的约束；软件回归和图像检查说明被覆盖场景的逻辑、内存和绘制行为；稳定帧率和音频恢复还需要对应版本的实板结果支撑。

如果没有完整实板数据，展示空白记录模板和待测项，比写未经测量的“稳定极限”更有说服力。

>
> 当前位流报告的最差 setup 为正 0.063 纳秒，hold 为正 0.012 纳秒。软件、渲染及对应范围的 HDMI 仿真有记录；上位机同时观察渲染、呈现、等待和欠载数据。仓库提供配套工程和产物，便于复现和继续测量。

## 六、答辩时容易被追问的十个问题

**1. 225 MHz 是什么？**  
当前 CPU／部分用户逻辑核心域频率。像素时钟、DDR 控制器侧、音频采样和逻辑更新是不同节拍。

**2. 为什么不用 CPU 直接画全部像素？**  
CPU 后端保留用于比较，但大面积重复像素操作适合专用数据通路；应用分支与状态仍适合 C 程序。

**3. 为什么四个帧缓冲，而不是两个？**  
流水运行时可能同时存在扫描帧、已请求帧和在途绘制帧，需要额外可用缓冲支持下一帧工作，并通过状态检查防止复用冲突。

**4. 透明效果是不是一定更慢？**  
它通常增加读改写及掩码成本，但具体取决于全局 Alpha、A8、分带窗口、缓存和路径条件，不能只看一个“开关”。

**5. TAB 可以提交任何临时数组吗？**  
不可以。硬件异步读表，数组和素材描述必须保持有效，直到相应完成条件成立。

**6. 上位机显示 35,200 就代表稳定 60 帧吗？**  
不代表。它是目标负载或容量，还要查看实际生效条件、呈现速率、最大帧时、重复帧与欠载。

**7. 提高核心时钟会让声音变快吗？**  
本设计中播放节拍由像素域的音频取样机制产生，核心侧按 FIFO 水位供样；时钟元数据错误会影响软件事件时机，但不应改变 ACR 采样率。

**8. 为什么语音替换时保留采样点数？**  
保证事件窗口、字幕、入场保护和大招动画不因音频长度变化而错位。

**9. 画面中的黑色矩形可能从哪里来？**  
除 RGB 素材外，还要检查 A8、透明边界、缓存一致性和 NOLOAD 区初始化，不能只凭颜色判断。

**10. 这个项目目前证明到哪一步？**  
可以按版本清单、时序、软件／渲染回归和实板记录分别回答。没有对应记录的负载稳定性、显示器兼容性或音质不作为已验证结论。
