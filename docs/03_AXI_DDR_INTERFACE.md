# 03 — AXI/DDR 访存、仲裁与数据吞吐

**对应报告：** 2.2.3.5。**源码：** [共享读仲裁](../rtl/blit/blit_axi_rd_arb.v)、[宽 AXI](../rtl/blit/blit_axi_wide.v)、[顶层](../rtl/ddr3_example_top.v)、[DDR 控制器](../rtl/ddr3_controller/ddr3_top.v)。

## 并发访存参与者

CPU 执行/状态、图形源读、命令表与分带桶读写、帧缓冲写入、显示持续扫描以及 PCM 读取争用共享外存。架构目标不是让某一个 DMA 永远吃满带宽，而是在显示不断流的约束下让渲染可持续推进。

### 已实现读仲裁的协议细节

`blit_axi_rd_arb.v` 的两个入口：`m0` 为 HDMI 扫描（高优先级），`m1` 为 BitBlt。主要行为：

- **地址通道：** 同时请求时优先 m0；`ARVALID=1 && ARREADY=0` 时用 `lock/lock_sel` 锁住赢家，直到该次握手，避免背压时改变 `ARADDR` 等信号。
- **返回通道：** 下游 `ARID={3'b000, sel}`；返回 `RID[0]` 进行 m0/m1 分流，`RLAST/RRESP/RDATA` 透传。
- **接收假设：** 代码中 `s_rready=1`，要求上游 DMA 在请求前已经为返回数据预留足够空间。它**不**是可处理任意 R 通道反压的通用 AXI4 交叉开关。
- 固定优先级对扫描有利，但在持续扫描请求下 m1 存在被饿死的理论可能；需通过性能计数/最坏延迟验证。

独立最小 Testbench 位于 [verification/axi_read_arb](../verification/axi_read_arb/)，验证仲裁、AR 锁定和 R 分流；完整高压力场景仍依赖系统级验证。

## 宽数据与带宽预算

- RGB565 720p 扫描：`1280 × 720 × 2 × 60.101 ≈ 110.78 MB/s`（仅有效像素读取）。
- 如每次输出新完整画面，还至少需要相近规模的目标帧写入，合计约 `221.56 MB/s`，未计背景/精灵/CPU/bin/PCM。
- 16-bit DDR3、400 MHz、双沿传输时**引脚物理理论带宽**为 `16×400M×2/8=1.6 GB/s`，实际可用吞吐低于该值。
- 128-bit 数据通路单 beat 恰好容纳 8 个 RGB565 像素。峰值吞吐仅适用于对齐、总线接纳、缓存等条件全部满足时。

工程采用连续短 Burst、FIFO、在途请求限制及 32→128-bit 桥接。DDR 实际效率受刷新、bank 命中、读写切换、总线竞争、FIFO 水位影响。不能仅用理论峰值推断 60 FPS。

## 需要额外收集的证据

| 计数器/事件 | 要回答的问题 |
|---|---|
| `PERF_RBEAT/PERF_WBEAT` | 各阶段读取和写入多少 beat |
| `qstall/tail_wait` | CPU 提交与加速器尾部等待是否是瓶颈 |
| `UF_CNT` / 音频欠流 | 高负载下显示、声音是否有断流 |
| bin 溢出与缓存命中 | 分带机制是否增加无法承受的元数据代价 |
| 95/99 分位帧耗时 | 平均 60 FPS 之外是否有抖动 |

未来改善建议先做压力档位固定的 A/B 测量，再调在途请求上限和缓存策略；不要无证据直接增加队列深度。
