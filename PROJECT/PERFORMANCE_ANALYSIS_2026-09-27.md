注：blit 是 gfx 统计的块拷贝调用次数；大部分新增是敌弹，但还包括背景、敌人等。它不含 fill 命令，不能直接等同于总命令数。`CPU 31 fps 29651 us` 是上次 CPU 模式的历史值，不是与当前状态同时测出的配对值。

**常态 32 FPS：** `queue` 几乎占满 `draw`，而尾部 `wait≈2 µs`。随着 blit 从 130 增到 4148，queue 增加约 8.24 ms，game 增加约 1.64 ms。此时 blt 约 43%，HDMI 仍 58–60/s，UF=0。连续的硬件满载或 DDR 总吞吐耗尽不是当前数据最直接支持的解释。CPU 准备命令、MMIO 写及可能的单帧队列背压共同占了提交时间。

如 blt% 时钟基准正确，32.2 FPS、43% busy 对应每帧平均约 13.4 ms 的引擎 busy 时间；当前 queue 约 25.9 ms。CPU 因队列满轮询的时间只可能发生在引擎忙的区间，因此 queue 中至少约 12.5 ms 不能归因于这种轮询。不过 13.4 ms 仍可能包含显著排队等待，必须直接测 qstall_us，不能仅凭 busy% 断言 CPU 计算是唯一瓶颈。

**偶发 12 FPS：** 同时出现 game=49–57 ms、blit≈4200、blt 掉到 16–17%，queue 只有约 27–28 ms。游戏逻辑突然变慢是这两次跌帧的直接原因。高度可疑的是 game.c:187–207：压力模式 `take_limit_shot` 找空弹位时最多扫描整个池；高档有 4096 个槽。128 个敌人有同步齐射机会，池接近满时每发都可能扫描大量槽甚至完整 4096 项，再计为 dropped shot。一次齐射可造成突发性长耗时；要结合 dropped_shots、弹池占用和齐射时刻确认。低 `blt%` 在这种窗口内也符合 CPU 长时间停留于 game_tick、没有给引擎供新命令。

`cpu 99%` 是当前统计口径下的 game+queue 占比，且 free 模式主循环没有主动休眠，不能作为“硬件未加速”的证据。`vs≈60/s` 只说明扫描器仍输出；实际新画面的提交速度是软件 fps。

下一轮优先级：先给 `take_limit_shot` 加一次扫描槽数/最大扫描槽数、分配失败数统计，并补 blit_push 的 qstall_us；再看 PERF_RBEAT/WBEAT 和较重的 alpha/小矩形对照。优化前先测量，避免把两个不同瓶颈混为一谈。

## 1. 初步结论

### 深入核对与离线实验补充

本轮新增 `analysis/perf_probe/`，只生成原 game.c 的计数副本，正式软件源文件和 RTL 未修改。

**时钟与缓存。** `ddr3_parameter.vh` 的 ASYN_AXI_CLK=0，因此 user_clk=core_clk；现有生成约束和 2026-09-26 时序报告给出的 core_clk 为 100 MHz，与 BLIT_CLK_MHZ=100 一致。SoC settings.json 指定 4 KB 单路 D-cache；生成 DataCache 网表有 64 个 tag 和 1024 个 32 位数据字、64 B 的补行请求。上述确认的是本地工程，不能替代核实开发板实际烧录版本。

**满弹池齐射的工作量已经复现。** 在原逻辑的独立计数副本上，固定高档 128 个敌人，令其同一 tick 齐射 5 发，得到：

| 齐射前活跃敌弹 | 发射尝试 | 检查弹槽次数 | 丢弃新弹 |
|---:|---:|---:|---:|
| 0 | 640 | 640 | 0 |
| 3900 | 640 | 1,822,720 | 444 |
| 4096 | 640 | 2,621,440 | 640 |
| 4096、该 tick 不齐射 | 0 | 0 | 0 |

Bullet 为 32 B，完整池为 128 KB。满池齐射反复遍历该池 640 次，地址跨度累计 80 MiB；在当前 4 KB、64 B 补行的缓存配置下，可造成大量重复 DDR 取数。这是逻辑算法制造的内存压力，不能笼统归咎于绘图加速器。80 MiB 是按遍历和缓存行推导的潜在读流量数量级，不是实测 DDR 计数。实际 CPU 周期未在主机上模拟。

所有高档敌人初始 attack_timer 相同，begin_run 一次生成 128 个敌人，存在同步齐射条件。用户日志的 game=49–57 ms 是窗口内每 tick 平均值；一次数百毫秒的慢 tick 也可能产生该平均值。因此下一轮应补 max_game_us，不能误读成每帧都恰好卡住 50 ms。

**HUD 的命令成本通过原渲染器计数。** 固定 4000 敌弹、128 敌人、无攻击预警等临时特效，设置日志相近的统计数字：

| 额外统计面板 | alpha | 总命令 | fill | blit | alpha 命令 | 面积≤4像素的 fill |
|---|---|---:|---:|---:|---:|---:|
| 开 | 开 | 7980 | 3718 | 4130 | 132 | 3706 |
| 关 | 开 | 6159 | 1900 | 4130 | 129 | 1892 |
| 关 | 关 | 6288 | 2158 | 4130 | 0 | 1892 |

这一固定场景下，f 关闭额外面板仍留下约 1900 条主要由文字生成的小 fill。用户日志 fill≈1900 的窗口也与额外面板已关闭的情况接近，不能预期再按 f 一定提速；必须确认当前开关状态。将主 HUD 字形缓存成精灵、合并横向连续笔画，才会减少这部分命令。e 关闭 alpha 后命令反而略增加，因为每个阴影变成两个普通 fill，说明该开关是综合对照，不是完全相同命令的纯 alpha 开关。

用户 32.2 FPS 窗口的末帧绘图调用为 1924+4148+133≈6205 条。将它视作代表帧，60 FPS 需要约 37.2 万条命令/秒，而 25.902 ms 的提交时间对应约 24 万条/秒。注意这些 gfx 计数是末帧值，queue 是窗口平均，故这里只作量级估计。

**硬件计算/调度上限做了小批量探测。** 使用仓库已有 Python Verilog 子集模拟器，快速 APB 输入 24 条命令，关闭模拟 HDMI，采用理想 ready/响应模型，三组都通过原 golden 像素比对：

| 操作 | 批量均摊时钟/命令 | 按 100 MHz 换算 |
|---|---:|---:|
| 1×1 普通 fill | 11.12 | 0.111 µs |
| 9×9 color-key copy | 71.54 | 0.715 µs |
| 9×9 color-key + 全局 alpha copy | 119.83 | 1.198 µs |

9×9 copy 的 24 条命令产生 216 次读 burst、225 次写 burst（部分行跨边界），符合短事务分析。这些结果只能说明本地模型下 RTL 核心没有固定卡在 30 多 FPS 的吞吐上限；未模拟真实 SoC 宽度转换、DDR 控制器、CPU 提交和并发访问，也不是独立的标准 RTL 仿真器验收结果。

**应按 60 FPS 重新理解 busy。** 当前 32.2 FPS、43% busy 对应约 13.35 ms busy/帧。如果保持同等每帧 busy 周期，提升到 60 FPS 将占约 80% 时间，而不是仍只占 43%。这不是未来实际利用率预测（提交节奏和并发会改变），但表明不能因为当前 busy<50% 就说硬件余量很大。

更新后的判断：常态吞吐应重点优化 CPU 到加速器的命令供给路径（含 MMIO、缓存/DDR 等待），并直接测量 qstall；满池卡顿有已经复现的算法工作量爆炸；加速器的小事务、alpha 排序及与 DDR 的配合仍有优化空间。优先减少无效扫描和 HUD 命令，再针对敌弹设计批量描述/短命令入口与约 648 B 的四种精灵片上缓存。单纯加深 FIFO 无法解决生产和消费端的持续吞吐问题。

实验输出：`analysis/perf_probe/results.txt`、`analysis/perf_probe/rtl_results.txt`。主机计数与理想模型时钟均不能替代实际板上耗时。

优先区分三件事：CPU 生成命令的成本、提交过程中队列满造成的等待、硬件处理小矩形/半透明命令的效率。现有板上日志把持续 DDR 原始带宽耗尽的可能性排在后面，仍需计数器验证。

“命令堆积”和“硬件/DDR 慢”可能是同一条因果链：下游执行慢 → 队列满 → CPU 在 blit_push 中轮询 → HUD 的 CPU% 升高。

每帧提交后 main.c 调用 blit_wait，等待引擎及其写响应全部完成，再翻页。因此当前结构不会正常地无限积压多帧绘图命令；主要观察的是单帧内的背压。增加队列深度只能吸收突发，不能提高下游持续吞吐。

## 2. 当前统计值的实际含义

软件路径前缀：`par/ddr_demo_ti60/embedded_sw/soc/software/standalone/game/src/`。

| 字段 | 实际计算/来源 | 不能据此直接断定的事 |
|---|---|---|
| game | main.c:551–566，含 bot_input 和 game_tick | 不是只有游戏碰撞计算 |
| queue | main.c:568–586，从准备渲染到 gfx_end | 包含场景遍历、敌人排序、文字展开、MMIO，以及 blit_push 等空位 |
| wait | main.c:581–588，所有命令提交完之后的 blit_wait | 不是本帧全部硬件等待时间 |
| draw | queue + wait | 不能再把 blt% 对应的时间加进去，CPU 与硬件已重叠运行 |
| cpu | main.c:603/613，HW 时为 (累计 game + 累计 queue)/窗口时间 | 不是处理器实际非空闲率，也不是纯计算比例 |
| blt | PERF_BUSY/窗口时钟数 | busy 包括排队、等读数据、等写响应，并不等于有效像素吞吐或 DDR 利用率 |
| fps | 软件提交完成帧的频率 | free 模式不是屏幕实际显示不同画面的频率 |
| vs | HDMI FRAME_CNT 差值 | 即使反复显示旧帧，仍可约 60/s |
| uf | 扫描 FIFO 下溢行数，累计值 | uf=0 不能排除 BitBlt 受 DDR 竞争影响；应看增量 |

关键源码：blit.h:107–118 的 blit_push 在 credits 为零时不断读 STATUS，直到出现空位。它发生在 queue 的计时区间。帧末 blit_wait 和等待 vsync 也都是轮询，但没有被计入 HUD 的 CPU%。

所以可能同时出现：CPU% 很高、queue 很长、wait 很短，而实际主要是等待硬件。也可能 CPU% 很低，但处理器仍在忙轮询。

## 3. 已确认的可疑路径

### 3.1 每颗敌弹是一条命令，但会变成多次短 AXI 事务

- render.c:45–47：四种 9×9 RGB565 子弹精灵。
- render.c:383–387：每颗活跃敌弹调用一次带 color key 的 gfx_blit。
- gfx_hw.c 的 hw_copy_common → blit_copy：参数通过 APB 寄存器提交，支持影子寄存器减少重复写。
- rtl/blit/blit_engine.v:295–309 和 814–818：读写按行组织，每段最大 64 beats，遇 256 字节边界拆分。

未裁剪的 9×9 敌弹至少产生 9 次源读 burst 和 9 次目标写 burst；跨边界时更多。写每行 5 个 32-bit beats，源读因对齐通常每行 5–6 beats。透明 key 通过 WSTRB 屏蔽写入，不能让整条源读和写通道事务消失。

以 2000 颗敌弹、60 FPS 为例：

- 敌弹绘图命令：120,000 条/秒，另有背景、敌人、HUD 等。
- 敌弹读写地址事务合计至少 2,160,000 次/秒。
- 9×9 的有效读写像素载荷是每颗 324 B；按当前对齐后的 AXI beats，约为每颗 360–396 B。
- 相应敌弹 AXI 读写载荷约 43.2–47.5 MB/s，不含地址/响应开销及 DDR 控制器内部放大。

这类负载可能先受短事务吞吐、延迟、行启动和流水间隙限制，而不是先碰到标称 GB/s 上限。当前 PIXEL 路径还要经过 C_ROW/C_WAIT，且新命令要等前一命令像素流水排空（c_load 的 ~pipe_busy），小图块的固定成本占比高。

### 3.2 每个半透明阴影都有排序等待

- render.c:298–307、317：逐个敌人绘制 alpha 阴影，再绘制敌人本体。
- 阴影带 A8 平面，即使全局 alpha=255 也需要混合。
- blit_engine.v:322：q_blend 或 q_sync 命令要等 drained。
- blit_engine.v:912–915：drained 包括先前像素流水、写 FIFO、写描述及 outstanding B 响应全部排空。

因此许多敌人的“阴影 → 本体 → 阴影 → 本体”会反复限制命令重叠执行。该等待是为正确叠加保留的依赖，不能直接删除。

可先按 e 做对照。若改善明显，说明 alpha 绘制路径重要；但 e 同时改变流量和命令形态，不能仅凭它确定全部成本来自 drained。后续应统计 alpha 排序等待周期。将阴影集中绘制也会改变遮挡关系，需要验证视觉语义。

### 3.3 HUD 文字不是一字一条命令

gfx.c:213–226 的 gfx_text 对每个亮点调用 gfx_fill_rect。一个 5×7 字符最多展开 35 个小矩形；一行文字会产生数百条命令，整个 HUD/面板可更多。

统计信息每 0.5 秒更新，但图形每帧仍然重新绘制。f 只关闭额外统计面板，不关闭全部 HUD，适合测量面板的增量成本。可在确认其成本后做字形缓存或水平连续像素合并。

### 3.4 CPU 逻辑也会随弹幕负载增长

- main.c:273 起的 bot_steer 扫描敌人、敌弹和宝石，并对附近对象计算带除法的避让。
- game.c:510 起遍历敌弹池、移动、寿命与玩家碰撞，主要随池容量/活跃数增长。
- game.c:482–507：玩家子弹逐个检查敌人；不能把敌弹误认为也和所有敌人做两两碰撞。
- game.c:184–199：压力模式找空弹槽，在池接近满时可能反复长扫描。
- render.c:365–370：敌人 Y 坐标插入排序属于 queue 时间，不属于 game。
- game_hostile_count 会在 HUD 中再次遍历弹池。

先看 game 时间，再用 b 关闭自动驾驶做短时对照，避免把 bot 成本当作加速器问题。长时间手动/自动对照会改变场景，应记录活跃敌弹数。

## 4. DDR 该怎么判断

640×480×2 = 614,400 B/帧。

按 60 FPS 估算，只计算有效像素载荷：

| 项目 | 每帧载荷 | 每秒载荷 |
|---|---:|---:|
| HDMI 扫描读 | 614,400 B | 36.864 MB/s |
| 每帧背景 copy 的源读 + 目标写 | 1,228,800 B | 73.728 MB/s |
| 以上基线合计 | 1,843,200 B | 110.592 MB/s |

敌弹、敌人、alpha、HUD、CPU 指令与数据访问另外增加。这个数不能用来证明 DDR 一定足够：端口宽度、短 burst 效率、仲裁、读写切换及实际 controller 吞吐都需要测。

rtl/blit/blit_axi_rd_arb.v:69 起，HDMI 请求优先于 BitBlt。因此扫描保持正常、uf 不增长时，BitBlt 仍可能被挤压。

当前 main.c 开机 benchmark 的 MB/s 对全屏 copy/alpha 只用 FB_BYTES 计算，是输出图像载荷速率；不能当作 DDR 总读写带宽。copy 和 alpha fill 至少应包含各一遍读和写。开机测试发生在 hdmi_enable 之前，也不能替代扫描开启时的并发测试。

已有硬件计数器可直接用于首轮测量，无需先改 RTL：

```text
0xF8101040  PERF_BUSY
0xF8101044  PERF_CMDS
0xF8101048  PERF_RBEAT
0xF810104C  PERF_WBEAT
0xF8101050  CMD_PUSHED
```

使用同一时间窗口的无符号差值：

```text
BitBlt 读载荷 MB/s = 4 × ΔRBEAT / elapsed_us
BitBlt 写通道载荷 MB/s = 4 × ΔWBEAT / elapsed_us
命令/帧 = ΔCMD_PUSHED / frames
```

上述只覆盖 BitBlt 的 AXI 通道，WBEAT 包含部分/全零 WSTRB 的 beats，不能直接代表实际 DDR 芯片有效写字节。还需加入 HDMI 和 CPU 等 master 才能讨论总流量。

PERF_CMDS 虽注释写 completed，实际在 w_cmd_done（最后一行最后一次写 burst 的内部发起）增加，并没有等到最后一个 B 响应；不能用 pushed-cmds 直接当硬件 FIFO 深度或 DDR 完成数。真正全帧完成仍以 BUSY 清零为准。STATUS 的 free slots 反映命令 RAM 空位；当前名义 256 项，另有 FIFO 输出预取寄存器。

## 5. 建议的最小测量改动（尚未实施）

第一步只修改软件统计，保持画面和执行顺序：

1. 在 blit_push 发现 STATUS 无空位时开始计时，直到出现空位；累加 qstall_us 和 qstall_events。不要每次轮询都读计时器。
2. 每帧记录 blit_st.cmds 差值，窗口输出命令/帧及峰值。
3. 每个统计窗口读取 RBEAT/WBEAT/PUSHED 差值。最好在帧完成边界取快照。
4. 输出 queue_total、qstall、queue_other=queue_total-qstall、tail_wait、game，以及各段峰值。queue_other 仍含 MMIO 事务延迟，不是纯指令计算。
5. 统计 game_tick 与 bot_input 的独立时间；必要时再拆 world/HUD，避免一开始过量插桩。
6. 记录 ΔUF、活跃敌弹/敌人数和工作帧耗时分布；使用低频汇总串口，避免每命令输出。

建议日志形态：

```text
fps=... game=... bot=... queue=... qstall=... tail=... max_work=...
cmd/frame=... shots=... blt_busy=... rd_MBps=... wr_MBps=... uf_delta=...
```

若软件统计仍不能区分，再给 RTL 加下面的周期计数器：

- CQ full 周期、队列占用峰值。
- 可执行 alpha/sync 命令因 !drained 阻塞的周期。
- PIXEL 的 C_WAIT 且 !row_ok 周期、C_RUN 且 !wf_credit 周期、c_issue 周期。
- ARVALID&&!ARREADY、AWVALID&&!AWREADY、WVALID&&!WREADY 周期。
- 尚有未返回读请求却无 RVALID 的周期；按 stream 分开可帮助定位源图/目标/A8 读。
- AR/AW 握手数与 beats 数，得到平均 burst 长度。
- 仲裁器中 HDMI 获得请求服务而 BitBlt 同时请求的周期。

这些计数可重叠，不应全部直接相加成 100%。RVALID 空档只有在确实存在 outstanding 请求时才有等待含义；高 AXI 背压也不自动等于 DDR 芯片带宽耗尽。

## 6. 不改源码即可进行的板上实验

先保存开机四项 benchmark 和轻/重负载各 5–10 秒的两行统计。确认输出后端是 HW、自动比较 c 为关闭状态；每次切换后丢弃首个统计窗口。

| 对照 | 操作 | 观察目的 |
|---|---|---|
| 同步限制 | v 切到 free，再恢复 | free 的 work 已超过约 16.67 ms 则不能持续 60 FPS；vsync 可能把略超预算放大为接近 30 FPS |
| alpha 增量 | e 开/关 | 判断阴影、面板及 alpha 路径是否占主要成本 |
| 统计面板增量 | f 开/关 | 判断大量小文字填充、面板 alpha 的影响；保留串口观察 |
| 自动驾驶 | b 开/关，短时比较 | 判断 bot 对 game 时间的贡献 |
| 扫描竞争 | t 彩条模式与 framebuffer 模式比较 | 当前 RTL 在彩条模式停止后续帧扫描 DMA，游戏仍渲染；通过串口看 work/queue/wait 是否改善 |
| 大块与小块 | n 切到方块/图像场景，+/- 调负载 | 大图快但小块慢，优先查命令/事务固定成本；两个都慢再加强内存路径排查 |

这些运行时开关会改变负载，属于筛查，不能保证完全等价。尤其 e 改变命令形态；b 改变玩家轨迹；n 切换场景也改变逻辑。更精确的测试应固定一份游戏状态，只重绘它，并独立控制敌弹数、HUD、alpha 和扫描。

不要直接用 p 暂停作为“只绘图”实验：render_game 在非 PLAYING 阶段额外做全屏 dim 和菜单绘制，会引入新的负载。

HDMI 配置标称约 59.97 Hz，59.9 附近本身不是掉帧；明显降至 50/40/30 等才需要按工作时间和错过翻页窗口判断。

## 7. 数据到结论的判定

| 观察 | 优先排查 |
|---|---|
| game 很大，qstall 很小 | 游戏逻辑、bot、弹池分配与内存访问 |
| queue_other 很大，硬件经常没活干 | CPU 遍历/文字生成/APB 提交效率 |
| qstall 很大 | 下游执行跟不上；继续看 alpha、像素等待、AXI 背压，不能止步于“队列太小” |
| blt_busy 高但 beats/周期很低 | 短事务、读延迟、排序等待或内部流水气泡 |
| 同等负载关闭扫描明显改善 | 共享读端口/DDR 服务竞争；仍不能只凭此认定 DDR 标称带宽耗尽 |
| alpha 关闭明显改善，alpha drain 计数高 | 优先处理 alpha 排序与绘图组织 |
| work 约 17–20 ms，vsync 约 30 FPS，free 约 50–59 FPS | 首先把帧工作压到预算以内，再检查翻页调度 |

当前建议先补 qstall 和每帧命令/AXI beats 统计，再决定优化方向。若确认是敌弹小图路径，可考虑四种精灵的片上缓存、减少按行启动成本、批量精灵描述；若是 HUD，做字形缓存；若是 alpha，同步优化必须保留覆盖与依赖语义。现阶段不宜仅扩大 FIFO 或提高 DDR 频率就预期解决问题。
